01 / Overview

From black box to open platform.

Statuses separate what is implemented from what is supported; a working component is not automatically a supported feature.

Working under hardening

Boot and recovery

The Linux 6.1 development line has a repeatable boot, recovery and A/B rollback path. Public installation remains gated on release documentation and tester validation.

Working under hardening

Wi-Fi and networking

Association, DHCP and gateway-liveness supervision are implemented. Driver-state recovery and longer-duration acceptance remain active work.

Working under hardening

Bluetooth media

Bluetooth SDP, A2DP sink and AVRCP service paths are implemented. Client compatibility and pairing hardening remain release work.

Working under hardening

Audio and AirPlay

AirPlay playback is hardware-validated through the current PCM path. Stream-start volume precedence remains an open safety investigation.

LibreEcho is active Linux 6.1 development for a specific Echo Gen 2 target — not a general-purpose upstream Linux port and not an unrestricted Open Beta.

03 / Supported hardware

Start with the exact target.

Initial development targets the Amazon Echo Gen 2 family on the MT8163 platform. A similar chipset, product name or enclosure does not prove compatibility.

Before downloading

  • Confirm that the device is an Amazon Echo Gen 2, not an Echo Dot, Show or another generation.
  • Record the model and board revision privately; never post the serial or MAC address.
  • Have a known-good USB data cable, a Linux/macOS/Windows host with documented USB tools, and a recovery path.
  • Back up owner-local state and connectivity firmware before any destructive operation.

Other Echo generations and unverified board revisions are unsupported. Hardware compatibility must be proven against the exact board and artifact, not inferred from marketing names.

04 / Install and recover

A safe path before a fast path.

The public release page will contain the downloadable release inventory when the next release is ready. The steps below explain the owner-facing installation and recovery process; destructive commands remain release-specific.

01

Prepare and back up

Confirm the supported model, host tools, cable and recovery method. Save original boot/recovery-critical state and owner-local calibration/connectivity inputs in a private, backed-up location.

02

Verify the release

Download only from the linked GitHub release. Verify the *-SHA256SUMS file and the published OTA public key before extracting or writing anything. Never use a raw image from a chat, branch or private path.

03

Install deliberately

Follow the release-specific partition and slot instructions. Stop if model, partition geometry, checksum, signing identity or owner-local inputs do not match. Destructive writes must name the exact target and require explicit confirmation.

04

First boot checklist

Confirm the product version, active slot, expected services, local Web UI response, read-write userdata and basic network/audio health. A Linux banner or ADB connection alone does not count as acceptance.

05

Update and rollback

Use the signed A/B updater only for an already-running compatible image. Keep the confirmed opposite slot. If health confirmation fails, preserve logs and use the documented recovery path; do not improvise a direct fastboot write.

06

Report safely

Include the exact public release identity, a smallest reliable reproduction and a redacted diagnostic bundle. Remove Wi-Fi secrets, provider tokens, serials, MACs, IPs, SSIDs, private paths and signing material.

Installation is not open yet: the public installation bundle and two independent first-time dry runs are still in progress. This guide explains the safety boundary; the Developer Preview is not yet open for general installation.

06 / Privacy and data flow

Local-first is not the same as local-only.

LibreEcho can keep substantial processing on-device, but configured providers and network services can receive data. Choose integrations deliberately and treat the Web Control Centre as a local network service.

Wake word and DSPIntended to run locally in the device service chain; quality and hardware privacy acceptance remain experimental.
STTLocal STT is an experimental development path. A configured external STT provider receives audio or transcript data according to that provider's contract.
AssistantProvider requests can contain the transcript, context or selected configuration. Review the provider before enabling it.
TTS and mediaLocal TTS payloads and AirPlay/Bluetooth media are separate paths; external sender/provider traffic follows its own network boundary.
Web UI, diagnostics and OTAKeep the control plane on a trusted LAN. Exports and diagnostics must exclude passwords, tokens and private telemetry; verify release signatures before updates.

Physical microphone privacy

Current state: physical mute is not a beta-supported privacy guarantee. The end-to-end hardware-derived input, capture-disable boundary, LED state and restart behavior remain release-gate work.

Software mute, a UI label or a daemon status field must not be interpreted as proof that the microphone hardware is disconnected or that capture cannot occur.

Secret handling

  • Use local account/session controls and protect credential files with restrictive permissions.
  • Do not place Wi-Fi credentials, provider tokens or signing keys in backups, issues or diagnostics.
  • Never expose the device API directly to the public Internet.

08 / Security and support

Send the right report to the right place.

Public issues are for reproducible, non-sensitive bugs. Never publish credentials, exploit details, OTA keys, private diagnostics or device identifiers in an issue.

Product bugReproducible behavior with redacted logs and public release identity.Question or design ideaUse Discussions when enabled; keep actionable defects in Issues.Join us on DiscordMeet the community, ask questions and follow the project’s development.Security vulnerabilityUse GitHub's private advisory route. Do not open a public issue for a vulnerability.

Bug report checklist

  • Product version, release tag and channel.
  • Generic Echo model/revision, without serial or MAC.
  • Smallest reliable reproduction and whether reboot/recovery changes it.
  • Redacted diagnostics with passwords, tokens, SSIDs, IPs and private paths removed.
  • Expected versus actual behavior and whether the issue is on the public release or a development build.

Support boundary

This is a volunteer Developer Preview project. There is no guaranteed response time, and direct public-Internet exposure of the device control plane is unsupported.

If GitHub does not show private advisory reporting for this repository, do not disclose the vulnerability publicly; wait for the maintainer-announced private route.

10 / Developer Preview

For recoverable hardware and careful testers.

The first cohort is bounded, technical and feedback-oriented. It is not a consumer launch.

Suitable testers

  • Own the specifically supported Echo Gen 2 target.
  • Can use command-line tools and USB recovery without maintainer-only access.
  • Have a backup and a known recovery path before changing the device.
  • Use a trusted local network and will not expose the control plane publicly.
  • Can submit redacted diagnostics and structured reproduction reports.

Entry acknowledgement

Installation may require recovery or reflashing and can cause data loss. Read the supported-hardware, privacy, known-issues and release pages first; verify checksums; preserve owner-local inputs; and understand that experimental voice, Bluetooth, physical mute and networking behavior may change.

Participation can be paused or withdrawn without deleting the public documentation. Open Beta will follow independent installation, recovery, OTA and stability evidence.

Feedback loop

  1. Record the public release identity and generic hardware scope.
  2. Reproduce with the smallest safe test.
  3. Collect and redact diagnostics.
  4. Use the product issue tracker for ordinary defects and the private security route for vulnerabilities.
  5. Link any release-blocking behavior to the current known-issues tracker.
Enrolment state: Developer Preview opening soon. The independent tester and release gates are still in progress.
